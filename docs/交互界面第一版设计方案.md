# Mini Agent 交互界面第一版设计方案

## 一、设计目标

第一版采用非全屏、持续交互的终端界面，整体体验接近 Claude Code，同时控制实现范围，不引入复杂的窗口布局和异步组件系统。

用户运行：

```bash
python3 main.py --workspace ./workspace/test_project
```

进入持续交互模式：

```text
╭──────────────────────────────────────────────╮
│ Mini Agent                                   │
│ Model: deepseek-chat                         │
│ Workspace: ./workspace/test_project          │
╰──────────────────────────────────────────────╯

❯ 修复当前失败的测试

● 正在分析任务...

● read_file
  path: tests/test_main.py
  ✓ 读取 1,284 字符

● write_file
  path: main.py
  ⚠ Agent 请求修改文件，是否允许？ [y/N/a]
  ✓ 写入 936 bytes

● shell
  command: python3 -m unittest discover -s tests -v
  ⚠ Agent 请求执行命令，是否允许？ [y/N/a]
  ✓ 14 tests passed

完成：修复了配置加载问题，所有测试已经通过。

❯
```

退出交互界面后进程才结束，用户不需要为每个任务重新启动程序。

## 二、第一版功能范围

### 必须实现

- 持续输入任务的 REPL
- 实时展示 Agent 当前状态
- 展示每一步工具调用
- 展示工具执行成功或失败
- 文件写入和 Shell 执行前确认
- 支持 `Ctrl+C` 中断当前任务
- 支持基本斜杠命令
- 保留当前单命令调用方式
- 输出过长时自动截断
- 最终结果使用 Markdown 渲染

### 暂时不做

- 全屏多窗口 TUI
- 鼠标操作
- 模型 token 级流式输出
- 多 Agent
- 并行工具调用
- 对话历史持久化
- 工具结果折叠动画
- 文件 diff 编辑器
- 跨进程恢复任务

第一版优先建立事件机制和权限机制，后续再考虑升级为基于 Textual 的全屏界面。

## 三、交互命令

建议支持以下命令：

```text
/help       查看帮助
/clear      清空屏幕
/status     查看模型、工作区和权限状态
/history    查看本次进程中的任务历史
/verbose    切换完整工具输出
/exit       退出程序
```

第一版暂时不支持运行时切换 workspace，因为工具实例已经绑定工作区。需要切换时应重新启动：

```bash
python3 main.py --workspace /another/project
```

## 四、界面状态设计

界面需要明确区分五种状态：

```text
○ Waiting     等待用户输入
● Thinking    等待模型响应
◆ Running     正在执行工具
✓ Completed   执行完成
✗ Failed      执行失败
```

工具展示采用统一格式：

```text
● search
  query: "AgentRuntime"
  path: .
  ✓ 找到 8 个结果
```

工具失败时：

```text
● read_file
  path: missing.py
  ✗ ToolError: file does not exist: missing.py
```

Shell 输出默认只显示摘要：

```text
● shell
  command: python3 -m unittest discover -s tests -v
  exit code: 0
  ✓ 14 tests passed
```

使用 `/verbose` 后显示完整的 stdout 和 stderr。

## 五、权限确认

工具按默认权限分为两类：

| 工具 | 默认行为 |
| --- | --- |
| `read_file` | 直接执行 |
| `search` | 直接执行 |
| `write_file` | 执行前确认 |
| `shell` | 执行前确认 |

确认界面：

```text
Agent wants to execute:

  python3 -m unittest discover -s tests -v

[y] 允许一次
[n] 拒绝
[a] 本次会话始终允许 shell
```

如果用户拒绝，不直接结束任务，而是向模型返回一个可恢复结果：

```json
{
  "success": false,
  "output": "execution denied by user"
}
```

模型可以据此调整方案或说明无法继续。

第一版的“始终允许”只对当前进程有效，退出程序后失效，不写入配置文件。

## 六、架构调整

当前 Runtime 采用一次性同步调用：

```python
state = runtime.run(task)
```

只有整个任务完成后，调用者才能获得结果，界面无法得知 Agent 正在调用模型还是执行工具。因此需要增加事件层：

```text
AgentRuntime
    │
    ├── 更新 AgentState
    └── 发出 AgentEvent
              ↓
         TerminalUI
```

建议定义以下事件：

```python
class EventType(StrEnum):
    RUN_STARTED = "run_started"
    MODEL_STARTED = "model_started"
    MODEL_COMPLETED = "model_completed"
    TOOL_REQUESTED = "tool_requested"
    TOOL_STARTED = "tool_started"
    TOOL_COMPLETED = "tool_completed"
    RUN_COMPLETED = "run_completed"
    RUN_FAILED = "run_failed"
```

事件对象：

```python
@dataclass(frozen=True)
class AgentEvent:
    type: EventType
    data: Mapping[str, Any]
```

Runtime 增加可选事件回调：

```python
def run(
    self,
    task: str,
    *,
    on_event: Callable[[AgentEvent], None] | None = None,
) -> AgentState:
    ...
```

内部统一发送事件：

```python
def emit(event: AgentEvent) -> None:
    if on_event is not None:
        on_event(event)
```

第一版选择同步回调而不是异步生成器，原因是：

- 对现有同步 Runtime 改动较小
- 不需要立即引入 `asyncio`
- 现有 `run(task)` 调用方式保持兼容
- 单元测试容易编写
- 后续仍可以增加 `async run_stream()`

## 七、权限机制设计

不应把 `input()` 写入 `AgentRuntime` 或具体工具中，否则核心逻辑会和终端 UI 耦合。

可以为 `ToolExecutor` 增加授权回调：

```python
PermissionHandler = Callable[[str, Mapping[str, Any]], bool]
```

执行流程：

```text
模型请求 write_file
        ↓
Runtime 发出 TOOL_REQUESTED
        ↓
PermissionHandler 询问用户
        ↓
允许 ──→ 执行工具
拒绝 ──→ 返回失败的 ToolResult
```

以后 Web UI 也可以提供自己的 `PermissionHandler`，不需要修改 Runtime。

## 八、建议目录结构

```text
Mini-Agent/
├── main.py
├── agent/
│   ├── events.py          # AgentEvent、EventType
│   ├── runtime.py
│   ├── state.py
│   └── prompt.py
├── model/
├── tools/
├── ui/
│   ├── __init__.py
│   ├── terminal.py        # REPL 主循环
│   ├── renderer.py        # 事件渲染
│   └── permissions.py     # 用户确认策略
└── tests/
    ├── test_events.py
    ├── test_terminal.py
    └── test_permissions.py
```

各模块职责：

```text
main.py             参数解析和组件装配
ui/terminal.py      接收用户输入
ui/renderer.py      把事件显示到终端
ui/permissions.py   危险操作确认
agent/runtime.py    执行 Agent Loop
tools/              实际操作环境
```

## 九、终端库选择

第一版建议引入 `rich`：

```toml
dependencies = [
    "rich>=13.0,<15.0",
]
```

Rich 可以直接提供：

- Markdown 渲染
- Spinner
- 彩色状态
- Panel
- Syntax Highlight
- 格式化异常
- 跨平台终端兼容

第一版不建议使用 Textual。Textual 更适合全屏应用，但会引入焦点、布局、异步任务和组件生命周期等额外复杂度。

如果坚持零第三方依赖，也可以使用 ANSI 转义符实现，但界面效果和跨平台稳定性会相对较弱。

## 十、运行模式兼容

保留两种运行模式。

交互模式：

```bash
python3 main.py --workspace ./workspace/test_project
```

不提供任务参数时进入 REPL。

单任务模式：

```bash
python3 main.py \
  --workspace ./workspace/test_project \
  "运行测试并修复失败项"
```

完成任务后直接退出，便于脚本或 CI 使用。

还可以增加跳过确认的选项：

```bash
python3 main.py --no-confirm "执行任务"
```

该参数启用时应明确显示安全风险提示。

## 十一、实施顺序

1. 新增 `AgentEvent` 和事件回调，不改变现有行为。
2. 为事件机制补充测试。
3. 增加独立的权限处理器。
4. 实现 Rich 事件渲染器。
5. 实现持续交互 REPL。
6. 加入斜杠命令和 `Ctrl+C` 处理。
7. 增加输出截断和 verbose 模式。
8. 更新 README 和使用示例。

## 十二、验收标准

第一版完成时应满足：

- 原有测试继续通过
- 单任务 CLI 仍然可用
- 无任务参数时进入持续交互界面
- 模型调用和工具调用有实时状态反馈
- `write_file`、`shell` 默认需要确认
- 拒绝工具后 Agent 能继续运行
- `Ctrl+C` 只中断当前任务，不退出整个程序
- `/exit` 能正常退出
- 工具的大段输出不会刷满终端
- UI 层不包含 Agent 的业务决策逻辑

## 十三、总结

第一版的核心定位是：

> 事件驱动 Runtime + Rich REPL + 工具权限确认。

它不仅是一次输出美化，还会为后续的流式响应、会话保存、diff 确认、Web UI 和全屏 TUI 建立稳定的扩展基础。
