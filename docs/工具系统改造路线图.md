# Mini-Agent 工具系统改造路线图

## 1. 背景与目标

Mini-Agent 已具备文件读写、文件搜索、Shell、网页搜索和 URL 抓取等基础工具，能够完成小型代码任务。当前主要瓶颈不是工具数量，而是权限边界、输出治理和长任务管理仍偏向教学原型。

本路线图参考 `/Users/bytedance/Desktop/claude-code` 中与工具系统相关的设计，重点借鉴以下模式：

- 工具使用结构化输入、输出 Schema，并在执行前统一校验。
- 工具显式声明只读性、并发安全性、破坏性和输出限制。
- 工具执行按“校验 → Hook → 权限 → 执行 → 输出治理 → Hook”分层。
- 长时间命令通过后台任务管理，而不是长期阻塞主循环。
- 权限按命令、路径和域名细分，而不是只按工具名称授权。
- 大型结果落盘，模型只接收有界预览和后续读取入口。

不直接复制 Claude Code 的复杂实现。本项目仍遵守以下原则：

- 保持 Python 代码简洁、模块边界清晰。
- 优先使用标准库，只有收益明确时才新增依赖。
- 保持模型响应为 `action` 或 `final_answer` JSON 对象的兼容协议。
- 工具失败尽量作为可恢复 Observation 返回。
- 先完成可靠的单 Agent 工具底座，再扩展 MCP、子 Agent 和 LSP。

## 2. 当前实现状态

当前生产入口静态注册以下工具：

- `read_file`
- `edit_file`
- `write_file`
- `find_files`
- `list_files`
- `search`
- `web_search`
- `fetch_url`
- `shell`

阶段一已完成：内置工具使用可执行的 JSON Schema 子集声明输入，`ToolExecutor` 在权限确认和执行前统一校验参数，并对旧式 `args_schema` 自定义工具保持兼容。工具也已声明只读性、并发安全性、破坏性和输出上限元数据。

当前工具系统仍有以下关键限制：

- `max_output_chars`、`concurrency_safe` 和 `destructive` 已进入工具契约，但尚未接入输出限制、并发调度和高危操作策略。
- Runtime 每轮只支持一个工具调用，所有工具同步串行执行。
- Shell 没有后台任务、增量输出、查询和停止接口。
- 会话级“始终允许”按工具名称授权，授权范围过宽。
- Shell 输出和传给模型的 Observation 缺少统一大小限制。
- `read_file` 会先读取完整文件，再应用行范围。
- Search 使用 Python 遍历和逐行扫描，能力与性能有限。
- Edit/Write 没有文件版本检查，无法发现读取后发生的外部修改。
- 工具在 `main.py` 中静态装配，没有 Hook、插件或 MCP 扩展点。

## 3. 总体架构

目标执行管线：

```text
Model action
    ↓
Tool lookup
    ↓
Input schema validation
    ↓
PreToolUse hooks
    ↓
Permission evaluation
    ↓
Tool execution / background task creation
    ↓
Output validation and limiting
    ↓
PostToolUse or PostToolUseFailure hooks
    ↓
Bounded Observation
```

目标工具契约示意：

```python
class Tool(ABC):
    name: str
    description: str
    input_schema: Mapping[str, object]
    output_schema: Mapping[str, object]
    read_only: bool
    concurrency_safe: bool
    destructive: bool
    max_output_chars: int

    @abstractmethod
    def run(self, args: Mapping[str, object]) -> str:
        ...
```

阶段一已建立这些契约字段。后续阶段应继续围绕同一契约演进，避免每增加一种能力就重新改写工具接口。

## 4. 改造阶段

### 阶段一：结构化工具契约与统一校验

状态：已完成。

目标：让参数错误在进入工具实现前被一致地识别，并为原生 tool calling、输出治理和并发调度提供基础。

实施内容：

1. 将工具参数定义从描述字符串升级为 JSON Schema 子集。
2. 增加统一输入校验器，至少支持：
   - `object`
   - `string`
   - `integer`
   - `number`
   - `boolean`
   - `array`
   - `required`
   - `enum`
   - 数值上下限
   - 是否允许额外字段
3. 为工具增加元数据：
   - `read_only`
   - `concurrency_safe`
   - `destructive`
   - `max_output_chars`
4. 保留当前 `describe()` 输出形式，让旧的自定义 JSON 模型协议继续可用。
5. 模型适配层预留原生 tool calling 接口；本阶段不要求立即删除文本 JSON 协议。
6. 参数校验失败继续以可恢复的 `ToolResult(success=False)` 返回。

主要文件：

- `tools/base.py`
- `tools/file.py`
- `tools/search.py`
- `tools/discovery.py`
- `tools/shell.py`
- `tools/web.py`
- `model/llm.py`
- `agent/runtime.py`

验收标准：

- 所有内置工具都有机器可校验的输入 Schema。
- 缺失字段、错误类型、未知字段和越界值返回稳定、可读的 Observation。
- 现有 `action` / `final_answer` 协议和测试保持兼容。
- 工具实现不再重复处理通用的类型和必填字段校验。

### 阶段二：工具输出预算、落盘与分页

目标：任何单次工具调用都不能无限占用进程内存或模型上下文。

实施内容：

1. 新增统一的 `ToolOutputLimiter`。
2. 工具可配置独立的字符上限；同时设置全局兜底上限。
3. 超过上限的文本结果写入会话数据目录，而不是 workspace。
4. 返回给模型的内容包含：
   - 截断说明
   - 原始字符数和行数
   - 头部预览
   - 尾部预览
   - 完整输出文件路径或结果 ID
5. 增加只读工具，用于按 offset/limit 读取落盘结果。
6. Shell 使用流式读取或临时文件，避免 `communicate()` 无限制缓冲。
7. `read_file` 按需读取指定行范围，并在读取前检查文件大小。
8. 会话清理策略需要覆盖过期工具输出，但不得误删仍被会话引用的数据。

建议新增模块：

- `agent/tool_output.py`
- `tools/output.py`

主要修改文件：

- `tools/base.py`
- `tools/shell.py`
- `tools/file.py`
- `agent/runtime.py`
- `agent/storage.py`
- `agent/session.py`

验收标准：

- 生成数十 MB 输出的命令不会把完整内容放入模型消息。
- 模型可以通过结果 ID 分页读取完整输出。
- 截断结果明确标识，不会让模型误以为输出完整。
- 取消、超时和失败时，已产生的输出仍可诊断。

### 阶段三：细粒度权限和高危命令保护

目标：将权限从“允许整个工具”升级为“允许明确能力范围”。

实施内容：

1. 引入统一权限规则：
   - `allow`
   - `ask`
   - `deny`
2. 权限规则支持会话级和持久级来源。
3. Shell 规则至少支持：
   - 精确命令
   - 命令及子命令前缀，例如 `git status:*`
4. 文件工具规则支持目录和 glob，例如 `src/**`。
5. URL 抓取规则支持域名，例如 `github.com`。
6. 解析 Shell 复合命令，至少识别：
   - `;`
   - `&&`
   - `||`
   - 管道
   - 重定向
7. 对破坏性操作增加独立检查，不能被宽泛的普通 allow 规则绕过。
8. 高风险类别至少包括：
   - 递归删除
   - 覆盖或清空大范围路径
   - `git reset --hard`
   - 强制推送
   - 修改系统目录
   - 下载后直接执行
   - 权限提升命令
9. 授权 UI 明确展示规则实际覆盖范围。

建议新增模块：

- `agent/permission_rules.py`
- `agent/command_policy.py`

主要修改文件：

- `agent/permissions.py`
- `ui/permissions.py`
- `tools/base.py`
- `tools/shell.py`
- `tools/file.py`
- `tools/web.py`

验收标准：

- 允许 `git status` 后，`git push` 仍需单独授权。
- 文件授权可以只覆盖一个目录。
- 域名授权不会自动放行其他域名或重定向目标。
- deny 规则优先于 allow 规则。
- 高危命令在 Full Access 以外始终有明确的安全路径。

### 阶段四：后台进程管理

目标：支持构建、测试、开发服务器和监控等长时间任务，同时保持主 Agent 可响应。

建议新增工具：

- `start_process`
- `read_process`
- `stop_process`

实施内容：

1. 后台进程使用 task ID 标识。
2. stdout/stderr 持续写入受控的会话数据目录。
3. 记录进程状态：
   - `running`
   - `completed`
   - `failed`
   - `cancelled`
4. `read_process` 支持：
   - 非阻塞查询
   - 有上限的等待
   - offset/limit 分页
5. `stop_process` 终止整个进程组，并保持跨平台降级策略。
6. Agent 或应用退出时清理未托管的子进程。
7. 后台进程必须复用阶段二的输出预算和阶段三的权限规则。
8. 第一版不实现完整交互式 PTY；有 stdin 需求时返回明确限制。

建议新增模块：

- `agent/tasks.py`
- `tools/process.py`

验收标准：

- 长命令启动后，Agent 可以继续执行其他操作。
- 可以查询增量日志、等待完成并主动停止任务。
- 取消主任务不会留下失控的孤儿进程。
- 后台输出不会无限增长。

### 阶段五：基于 ripgrep 的增强搜索

目标：提升大型仓库搜索速度和表达能力，同时保留无 `rg` 环境下的可移植性。

实施内容：

1. 系统存在 `rg` 时优先使用 `rg`。
2. 缺少 `rg` 时回退到现有 Python 搜索实现。
3. Search 增加：
   - 忽略大小写
   - 前后文行数
   - 文件 glob
   - 文件类型
   - 多行模式
   - `content`
   - `files_with_matches`
   - `count`
   - offset/limit 分页
4. 尊重 `.gitignore` 和常见 ignore 规则。
5. 结果返回总匹配数、文件数和是否截断。
6. `find_files` 同样可以优先使用 `rg --files`，并保留 Python fallback。

主要文件：

- `tools/search.py`
- `tools/discovery.py`
- `agent/diagnostics.py`

验收标准：

- Search 参数覆盖日常代码检索需求。
- 大型目录搜索不会因逐个打开所有文件而明显阻塞。
- 有无 `rg` 时输出契约保持一致。
- 截断和分页信息明确。

### 阶段六：安全文件读取和乐观并发编辑

目标：防止大文件拖垮进程，并避免覆盖用户或格式化工具在 Agent 读取后产生的修改。

实施内容：

1. `read_file` 在读取前检查文件类型和大小。
2. 二进制文件返回类型、大小等元数据，不按 UTF-8 强行解码。
3. 文本读取返回内容 hash 或版本 token。
4. `edit_file` 和覆盖已有文件的 `write_file` 支持 `expected_hash`。
5. hash 不匹配时拒绝写入，并提示模型重新读取。
6. `edit_file` 增加显式 `replace_all`。
7. 写入使用同目录临时文件加原子替换，尽量避免半写入状态。
8. 保持当前唯一匹配保护和 unified diff 输出。

主要文件：

- `tools/file.py`
- `tools/base.py`
- `ui/permissions.py`

验收标准：

- 大文件和二进制文件不会被无界读入内存。
- 读取后被外部修改的文件不能被静默覆盖。
- 单处替换与全局替换语义明确。
- 写入失败不会留下部分内容文件。

### 阶段七：只读工具并行执行

目标：减少仓库探索阶段的模型往返时间，同时保持写操作顺序确定。

实施内容：

1. 协议允许一次响应包含多个 action，同时继续接受旧的单 action 格式。
2. 根据工具元数据划分执行批次。
3. 初始可并行工具：
   - `read_file`
   - `find_files`
   - `list_files`
   - `search`
   - `web_search`
   - `fetch_url`
   - `read_process`
4. 写工具和无法判断的工具串行执行。
5. 对同一路径的潜在冲突操作强制串行。
6. 结果按模型请求顺序写回，避免并发完成顺序导致上下文不稳定。
7. 一项工具失败不应自动取消无依赖的其他只读工具；取消整个 Run 时则全部终止。

建议新增模块：

- `agent/tool_scheduler.py`

主要修改文件：

- `agent/runtime.py`
- `agent/state.py`
- `agent/events.py`
- `tools/base.py`
- `model/llm.py`
- `ui/renderer.py`

验收标准：

- 多个独立只读工具可以并行运行。
- 文件写入与 Shell 默认不会并行。
- 结果顺序稳定，取消能够传递给所有运行中的工具。
- 旧模型的单 action 响应不受影响。

### 阶段八：Tool Hook API

目标：让格式化、审计、策略检查和失败诊断可以扩展，而无需直接修改 ToolExecutor。

第一版 Hook：

- `pre_tool_use`
- `post_tool_use`
- `post_tool_failure`

Hook 能力边界：

- `pre_tool_use` 可拒绝调用或返回修改后的参数。
- `post_tool_use` 可附加上下文，但默认不能把失败改成成功。
- `post_tool_failure` 可提供诊断信息。
- Hook 超时和失败作为独立事件记录。
- Hook 默认按注册顺序执行；暂不支持复杂并行聚合。
- 外部命令 Hook 必须受 workspace trust 和权限规则约束。

建议新增模块：

- `agent/hooks.py`

主要修改文件：

- `tools/base.py`
- `agent/runtime.py`
- `agent/events.py`
- `agent/config.py`

验收标准：

- 可以通过 Hook 在文件修改后运行 formatter。
- 可以在 Shell 执行前阻止团队禁止的命令。
- Hook 失败不会破坏会话协议或吞掉原始工具结果。

### 阶段九：插件与 MCP

目标：不修改核心源码即可接入外部工具。

实施顺序：

1. Python entry point 或本地模块插件。
2. 工具命名冲突、启用/禁用和版本诊断。
3. stdio MCP client。
4. MCP 工具映射到统一 Tool 契约。
5. MCP 调用超时、取消、权限和输出预算。
6. 工具数量增长后增加延迟加载和工具搜索。

不在第一版实现：

- 远程 MCP OAuth 全流程。
- 插件市场。
- 自动安装第三方代码。
- 未经用户配置自动连接远程工具。

验收标准：

- 外部工具使用与内置工具相同的校验、权限和输出治理。
- 单个插件或 MCP 服务失败不会阻止核心工具启动。
- 模型上下文不会因大量未使用工具 Schema 无限制增长。

### 阶段十：子 Agent 与 Worktree

目标：为大型只读探索和隔离式实现任务提供委派能力。

实施顺序：

1. 只读 `delegate_task`，限制可用工具和步数。
2. 子 Agent 独立 token/输出预算和取消信号。
3. 后台子 Agent 复用统一任务系统。
4. 支持结果摘要和完整结果文件。
5. 写任务必须使用临时 Git worktree。
6. 明确 worktree 创建、保留、合并和清理策略。

验收标准：

- 子 Agent 不能越过父任务授予的权限。
- 多个只读 Agent 可以并行探索不同模块。
- 写 Agent 不直接并发修改主工作区。
- 父 Run 取消后子 Agent 和后台任务都能收敛退出。

### 阶段十一：专业工具

底座稳定后，再按实际用户需求选择：

- LSP：定义、引用、符号、实现、hover、调用层级。
- Notebook：结构化读取和 cell 级编辑。
- Image/PDF：多模态读取或分页提取。
- Browser：JavaScript 页面、登录态和交互自动化。
- Task/Todo：模型可见的长任务计划和依赖管理。

这些工具均不应绕过前面阶段建立的 Schema、权限、输出预算、取消和 Hook 管线。

## 5. 版本里程碑

### M1：可靠工具底座

包含阶段一至阶段三：

- 结构化 Schema
- 输出预算
- 细粒度权限

完成后，工具数量基本不变，但安全性和稳定性显著提升。

### M2：可处理真实长任务

包含阶段四至阶段六：

- 后台进程
- ripgrep 搜索
- 文件版本保护

完成后，可以更可靠地运行构建、测试和大型代码库检索。

### M3：效率与扩展性

包含阶段七至阶段九：

- 只读并行
- Hook
- 插件与 MCP

完成后，工具系统从静态内置集合演进为可扩展运行平台。

### M4：高级 Agent 能力

包含阶段十和阶段十一：

- 子 Agent
- Worktree 隔离
- LSP、Notebook、Browser 等专业工具

## 6. 测试策略

每个阶段都必须增加聚焦测试，不依赖只在开发者机器上可用的命令或权限。

核心测试类型：

- Schema 参数正确、缺失、类型错误、额外字段和边界值。
- 权限 allow/ask/deny 优先级和规则范围。
- Shell 复合命令及高危命令测试。
- 超大输出落盘、截断、分页和清理。
- 后台任务启动、增量读取、完成、失败、取消和孤儿清理。
- 文件 hash 冲突和原子写入。
- 有 `rg` 与无 `rg` 两种搜索路径。
- 并行工具顺序、冲突串行化和取消传播。
- Hook 修改输入、拒绝、超时和异常。
- 插件/MCP 部分失败隔离。

每次实现完成前执行：

```bash
python -m unittest discover -s tests -v
python -m compileall -q agent model tools ui main.py
git diff --check
```

涉及打包或插件发现时额外执行：

```bash
python -m build
```

并在完成后移除 `build/`、`dist/` 和 `mini_agent_runtime.egg-info/` 等生成物。

## 7. 明确暂不纳入的能力

为保持 Mini-Agent 的边界，当前路线图不计划照搬以下平台型能力：

- Cron 和远程触发。
- 推送通知和 PR 订阅。
- 多人 Agent 团队通信。
- 企业 Vault 和远程执行环境。
- 插件市场与自动下载安装。
- 完整工作流编排器。
- 终端面板、远程控制和桌面端集成。

只有出现明确用户场景后，才应把这些能力加入后续路线图。

下一次实现任务进入阶段二，先完成一个可独立验证的输出治理切片：

1. 定义统一的全局输出上限，并将工具自身的 `max_output_chars` 纳入决策。
2. 在 `ToolExecutor` 成功路径中截获超限输出，返回明确的截断说明和有界预览。
3. 将完整输出写入受控的会话数据目录，而不是 workspace。
4. 为落盘结果增加稳定的结果 ID 和分页读取工具。
5. 覆盖短输出、超大输出、失败、取消和过期清理测试。

该切片稳定后，再改造 Shell 的流式采集和 `read_file` 的按需读取；后台任务、MCP 和子 Agent 仍按路线图顺序后置。
